Claude Code Hooks
配置体系与 Stop Hook 闭环防治深度解析

当 AI Agent 通过 Hook 注入 Lint 反馈时，如何避免无限循环？本文拆解 Claude Code 的配置层级、Hook 机制及其防闭环方案，供技术分享与方案参考。

1配置层级：五层 Deep Merge

Claude Code 从五个来源读取配置，按优先级从低到高 深度合并（deep merge），高优先级的键覆盖低优先级：

层级 路径 范围 Git 优先级
User ~/.claude/settings.json 当前用户所有项目 — 最低
Project .claude/settings.json 当前项目（团队共享） 提交 中
Project Local .claude/settings.local.json 当前项目（个人） gitignore 中高
CLI --settings <file> 本次运行 — 高
Enterprise 托管策略 组织全员 — 最高
合并规则：标量字段（如 model）高优先级覆盖；对象/数组字段（如 permissions）深度合并。同级配置不会互斥，而是逐层叠加。 
// ~/.claude/settings.json (User)
{ "permissions": { "allow": ["Read"], "deny": [] } }

// .claude/settings.json (Project)
{ "permissions": { "allow": ["Edit"] } }

// .claude/settings.local.json (Local)
{ "permissions": { "deny": ["Bash(rm -rf:*)"] } }

// ============ 合并结果 ============
{ "permissions": { "allow": ["Read", "Edit"], "deny": ["Bash(rm -rf:*)"] } }

2Hooks 机制：三种类型 × 十五种事件

Hook 类型

type 作用 是否消耗 Token
command 执行 shell 命令 否
prompt 注入文本到对话上下文 是（注入量）
agent 启动子 Agent（独立 Claude 实例） 是（较多）

核心事件与 Exit Code 语义

事件 触发时机 exit 0 exit 2
PreToolUse 工具执行前 允许 阻止 + stderr 反馈给 Claude
PostToolUse 工具执行后 正常 stderr 仍反馈（不阻止，已执行）
Stop Claude 完成回复 允许停止 阻止停止 + 注入反馈 → Claude 继续
关键：Stop hook 的 exit 2（或 prompt/agent 类型）会阻止 Claude 停止，并将输出注入对话，让 Claude 继续工作。这正是闭环的根源。

3Stop Hook 闭环问题

当 Stop hook 用于"检查 Lint / 验证完成"时，极易形成无限循环：

① Stop 触发
Claude 完成回复
→
② Hook 检测到问题
exit 2 / prompt 注入
→
③ Claude 继续
看到反馈，尝试修复
→
④ 完成 → Stop 再触发
回到 ①
↻ 无限循环
真实案例：Reddit 用户反馈，Stop hook 中调用了 claude 命令，形成递归循环，日均消耗 $3600。这是 Claude Code 社区的高频踩坑点。

4Claude Code 的防闭环方案（两层防护）

第一层：硬熔断（源码内置，确定性）

源码逆向确认：提取 Claude Code 原生二进制（197.5MB）字符串常量交叉验证——Stop hook 连续 block 8 次后强制终止。可通过环境变量 CLAUDE_CODE_STOP_HOOK_BLOCK_CAP 覆盖。这是确定性的硬上限，不依赖 AI 是否"听话"。

第二层：stop_hook_active 标志位（提示词约定，非确定性）

社区的标准做法是在 Stop hook 的 prompt 中加入一个"标志位约定"，告诉 Claude 如果已经处于 hook 激活状态就不再触发： 

{
  "hooks": {
    "Stop": [
      {
        "type": "prompt",
        "command": "Before finishing, verify:\n1. Did you run lint?\n2. Are there TODO comments left?\nIf any check fails, continue working.\n\nIMPORTANT: If stop_hook_active is true in your context,\ndo NOT trigger this check again — just finish."
      }
    ]
  }
}
原理：第一次 Stop 时，Claude 读到 prompt → 开始检查 → 将 stop_hook_active 置为 true → 继续工作。第二次 Stop 时，Claude 读到 prompt 但发现 stop_hook_active 已为 true → 遵守约定直接停止。

此方案的局限性

问题 说明
非确定性 完全依赖 LLM 遵守提示词约定。AI "可能听，可能不听"，无强制力
无计数 / 去重 不跟踪"同一错误已提示几次"，不区分"错误是否变化"
无熔断 没有"达 N 次后硬性停止"的后备保护
状态不可靠 stop_hook_active 存于对话上下文，compaction（压缩）后可能丢失

5总结：Claude Code vs 理想方案

维度 Claude Code（现状） 理想方案
配置层级 5 层 deep merge（user→project→local→CLI→enterprise） 借鉴层级 + 按 session/repo/user 分级
Lint 注入方式 PostToolUse stderr → Claude（单轮，不触发新对话） tool.execute.after 注入 output.output（同）
防闭环机制 硬熔断 8 次 (STOP_HOOK_BLOCK_CAP) + 提示词 guard 指纹去重 + maxHints（per-file，区分错误变化）
忽略机制 无（只能靠提示词告诉 AI 忽略） mode: silent / notify + ignore glob
熔断保护 无 maxHints 硬上限 + 指纹变化重置
核心启示：Claude Code 实际有两层防护——硬熔断（8 次 block cap，确定性）兜底 + 提示词 guard（软约定）辅助。但 8 次是全局连续计数，不区分文件、不区分错误是否变化。指纹去重方案更精细：per-file 追踪、同错误有限次、变了重置、clean 归零——避免对"修了一半的错误"误杀。
